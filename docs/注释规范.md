# 注释规范

> 注释纪律的单一事实源：项目 AGENTS.md 内联的摘要与本文件冲突时，以本文件为准。
> 语言：**中文**（技术名词保留英文原词，不翻译）。注释随代码走，不是独立动作。

## 原则

1. **注释写 why，代码写 what。** 代码本身能看出来的，不写注释。
2. **注释自包含——代码是第一信息获取源。** 不写「详见 docs/xxx」「方案 §N」「见
   某观察文档」这类外指：注释要成立，必须把约束/背景/口径本身写进注释里，而不是
   让读者去别处查。文档可以存在，但代码注释不依赖它。
3. **陈述现状与不变式，不陈述历史。** 注释是给「半年后读代码的人」看的——他不知道
   旧行为是什么，「不再…」「已退役…」「修了…」这类变更日志式注释会随时间失效。
   历史进 commit message；注释里只留对新读者仍有价值的部分（约束的证据、事故的后果）。
4. 注释密度向「藏 complexity 的地方」倾斜：并发与生命周期纪律、持久化与副作用时机、
   编码/精度等边界、跨模块契约顺序——这些是注释的主战场；普通业务代码保持稀疏。

## 注释标记（统一前缀，可 grep）

| 标记 | 用途 | 示例 |
|------|------|------|
| `NOTE:` | 代码看不出来的约束/设计决定 | `NOTE: 此回调在锁内执行——禁止再调任何会拿同一把锁的接口，否则死锁` |
| `踩过:` | 违反上述约束的真实事故（接在 NOTE 后作证据） | `踩过: 曾在锁内直接广播事件，卡死整个循环` |
| `TODO:` | 已知的待办，写明方向 | `TODO: 轮询等待可改为事件驱动` |
| `HACK:` | 明知的取巧，说明为什么可以接受 | — |

## 各位置的写法

### 文件头（每个源码文件）

一段职责说明 + 关键设计决定（**自包含**——不指向方案/设计文档，背景写进注释本身）。
注释符号随语言（`//` / `#` 等）。不加版权/license 头——**闭源开发期不需要**；将来
公开时统一补 SPDX 行（`// SPDX-License-Identifier: <协议>` + 版权行），到时一次性
脚本处理，平时不写。

### 分节横幅

大文件用分节横幅切开：`// ---- 分节名 ----`（Python/Shell 用 `# ---- 分节名 ----`），
节名说职责不说过渡（写「会话注册表」不写「辅助函数」）。


### 公开面必须补文档注释（内部函数保持稀疏）

每个对外导出的符号——模块级导出函数/类、HTTP/IPC 端点 handler、公开头文件函数——
用所用语言的标准文档注释写一段：**职责 + 何时触发副作用（请求/落盘/广播）+ 失败
行为**；参数与返回值仅在语义不自明时标注。格式随语言：

- Python 公开函数用 docstring：

  ```python
  def enter_draft(ws: str | None = None) -> Draft:
      """进草稿态：新建后的空态引导。零副作用——注册表/磁盘在首条消息前不动。"""
  ```

- JS/TS 导出用 JSDoc（职责一句；`@param`/`@returns` 仅在语义不自明时写）。

### 事件与契约注释

跨端点/跨事件的隐式契约必须写在**生产者处**（消费者处可留一行指回）：广播顺序、
emit 顺序、字段语义。生产者注释要写明消费者会依赖的承诺，如「先广播用户消息再开
下一阶段（顺序保证）」。

## 反面清单

- ✗ 复述代码：`# 遍历列表`（for 循环自己会说话）
- ✗ 变更日志：`已改为 X` / `不再 Y` / `以前是 Z`（历史归 commit）
- ✗ 对话式注释（对评审者说话）：`这里先这样，后面优化`——要么 TODO 要么删
- ✗ 注释掉的死代码——git 会记得，直接删
- ✗ 英文注释混入（技术名词/标记前缀除外）
